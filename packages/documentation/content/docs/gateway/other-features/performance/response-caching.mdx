Response caching lets Hive Gateway reuse previously computed GraphQL `query` results and return them
without re-running query planning and subgraph execution.

Use it to reduce latency, lower subgraph traffic, and improve stability during traffic spikes.

## Before You Start

<Callout>
  Configure a cache storage in your gateway config first. See [Cache
  Storage](/docs/gateway/other-features/performance#providing-cache-storage).
</Callout>

Key behavior to keep in mind:

- Only `query` operations are cached.
- `mutation` and `subscription` operations are never cached.
- Responses can still be invalidated by mutation results (enabled by default).

## Quick start

Enable response caching globally for public data:

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    // null = shared/public cache bucket
    session: () => null,
  },
});
```

With this setup, repeating the same query can be served directly from cache:

```bash
curl -X POST http://localhost:4000/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"{ slow }"}'
```

## Choose a caching strategy

The same `@cacheControl` directive can be interpreted differently depending on your setup.

### Cache in Hive Gateway (recommended)

Use Gateway Response Caching when you want both:

- fewer calls from gateway to subgraphs on cache hits
- mutation-based invalidation support in gateway

This works well when your subgraphs expose `@cacheControl` in the supergraph.

### Cache with HTTP headers (`Cache-Control`/`ETag`)

If your subgraphs already expose HTTP cache headers, pair that with Gateway HTTP Caching.

- This can reduce network payload size and computation.
- Depending on headers/validation flow, it may still require gateway-to-subgraph HTTP requests.

See [HTTP Caching](/docs/gateway/other-features/performance/http-caching).

### Cache inside each subgraph

If caching runs only at subgraph level, subgraphs do less work on repeated requests, but the gateway
still sends requests to subgraphs for each query.

## Use `@cacheControl` from subgraphs

To let gateway-level response caching use schema directives, compose `@cacheControl` into your
supergraph:

```graphql
extend schema
  @link(
    url: "https://specs.apollo.dev/federation/v2.1"
    import: ["@composeDirective"]
  )
  @link(url: "https://the-guild.dev/mesh/v1.0", import: ["@cacheControl"])
  @composeDirective(name: "@cacheControl")

enum CacheControlScope {
  PUBLIC
  PRIVATE
}

directive @cacheControl(
  maxAge: Int
  scope: CacheControlScope
  inheritMaxAge: Boolean
) on FIELD_DEFINITION | OBJECT | INTERFACE | UNION
```

Then define cache behavior in your schema:

```graphql
type Query {
  me: User @cacheControl(maxAge: 5, scope: PRIVATE)
  products: [Product!]! @cacheControl(maxAge: 60)
}

type Product @cacheControl(maxAge: 300) {
  id: ID!
  name: String!
  price: Float!
}
```

## Session-aware caching (prevent user data leaks)

Use `session` to separate cache entries by user or group.

### Per-user cache key

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: (request) => request.headers.get("x-user-id"),
  },
});
```

### Per-role (group) cache key

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: (request) => request.headers.get("x-user-role"),
  },
});
```

<Callout type="warning">
  Always derive session keys from validated authentication context. Never use
  untrusted user input directly as a cache partition key. See
  [Authorization/Authentication](/docs/gateway/authorization-authentication).
</Callout>

### Require session for private fields

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: (request) => request.headers.get("x-user-id"),
    scopePerSchemaCoordinate: {
      "Query.me": "PRIVATE",
      User: "PRIVATE",
    },
  },
});
```

## Set TTLs

By default, cached operations are stored indefinitely unless you configure a TTL. Set TTLs to reduce
stale data risk.

### Global + per-field/type TTL

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: () => null,
    // default TTL for cached operations (milliseconds)
    ttl: 2_000,
    ttlPerSchemaCoordinate: {
      Product: 60_000,
      "Query.flashSale": 5_000,
    },
  },
});
```

If a query includes multiple cached objects with different TTLs, the lowest TTL is used.

### Disable caching for specific fields/types

Set TTL to `0` for data that should never be cached:

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: () => null,
    ttlPerSchemaCoordinate: {
      DateTime: 0,
      "Query.currentTime": 0,
    },
  },
});
```

## Request-Level Controls

### Disable caching globally in development

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: () => null,
    enabled: () => process.env.NODE_ENV !== "development",
  },
});
```

### Skip caching for specific requests

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: () => null,
    enabled: (request) => request.headers.get("x-no-cache") !== "true",
  },
});
```

## Invalidation via mutation results

When a mutation returns entities, Hive Gateway invalidates cached query results containing those
entities.

```graphql title="mutation"
mutation UpdateUser {
  updateUser(id: "1", name: "John") {
    __typename
    id
    name
  }
}
```

If the result includes `User` with `id: "1"`, cached query responses containing that entity are
invalidated.
The gateway uses `__typename` and identity fields (by default `id`) from mutation results to match
and invalidate related cached query entries.

Disable this behavior if needed:

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: () => null,
    invalidateViaMutation: false,
  },
});
```

### Customize entity identity

By default, entity identity uses `id`. You can provide additional identity fields:

```ts title="gateway.config.ts"
import { defineConfig } from "@graphql-hive/gateway";

export const gatewayConfig = defineConfig({
  responseCaching: {
    session: () => null,
    idFields: ["id", "email"],
  },
});
```

## HTTP revalidation support (`ETag`)

Response Caching also supports HTTP revalidation with `ETag` and `If-None-Match`.

When clients send `If-None-Match` matching the current `ETag`, gateway can return:

- `304 Not Modified`
- no response body

This is useful for browser and client-side caching behavior.
